01 / Overview

Executive summary

The supplied candidate progress page presents a multi-stage application workflow and a form for submitting a primary deliverable link, up to four additional links, and optional execution notes. The page also displays profile attributes that are personal data. One visible data-consistency concern is that the identifier in the page URL does not match the reference code displayed in the page.

This review did not make direct API requests, submit forms, test access controls, or inspect server configuration. Therefore, it identifies review items and improvement opportunities, not confirmed vulnerabilities. The most useful next step is to verify server-side candidate authorization and the record-to-reference-code mapping in an authorized test environment.

03 / Observed surface

Observable architecture and data flow

From the browser, the page behaves like a web application that renders a candidate-specific progress dashboard. The visible information is organized into application screening and technical assessment stages. The second stage presents deliverable instructions alongside a form with a required primary link, an option to add up to four more links, and optional notes.

What can be stated: candidate-profile fields and workflow details are rendered in the page; the submission UI allows a bounded number of links. What cannot be inferred: whether rendering is server-side or client-side, which API or database is used, how sessions are stored, and whether server-side validation or authorization is implemented.

A safe conceptual request flow is: authenticated candidate session → server checks ownership of the application record → service validates the submission → persistence layer records it → response returns a minimal status. Each step should be enforced by the backend even if the UI also applies convenience checks.

04 / Proposed interface

API structure and payload model

Observation limit: the page snapshot did not expose actual API routes, request bodies, response bodies, or status codes. The following is a proposed contract derived from the visible workflow, not a claim about Cynbit's implementation.

Read progress

GET /api/v1/candidate/applications/{applicationId}/progress

{
  "referenceCode": "candidate-facing-code",
  "role": "Backend Developer Intern",
  "stage": "technical_assessment",
  "timeline": [
    { "key": "screening", "status": "complete" },
    { "key": "technical_assessment", "status": "active" }
  ],
  "deliverable": {
    "additionalLinkLimit": 4,
    "submissionStatus": "not_submitted"
  }
}

Submit deliverables

POST /api/v1/candidate/applications/{applicationId}/deliverables

{
  "primaryUrl": "https://example.org/report",
  "additionalUrls": [],
  "notes": "Implementation notes"
}

Suggested success response: 201 with a submission ID, received status, and timestamp. Store only what the workflow needs.

Suggested error shape: return stable machine-readable error codes and a request ID, for example {"error":{"code":"VALIDATION_ERROR","message":"Check the submitted fields","requestId":"..."}}. Use consistent 401/404/409/422 responses as appropriate; do not return stack traces, database details, or another candidate's data. Actual error behavior was not tested.

The candidate-profile fields visible in the page are personal data. If needed by the screen, return only the minimum fields, only after authenticating the candidate and checking application ownership. The display reference code should be sourced from the same authorized application record as the status and submission.

05 / Review items

Security, correctness, and performance findings

Medium · Verify

Candidate data requires a strict server-side access boundary

Category: privacy / authorization. Confidence: high that personal-data categories are displayed; no conclusion about server authorization.

Evidence: the progress page displays candidate identity and contact, education, and location attributes. The page URL contains a candidate-specific identifier. The visible page alone does not establish whether an authenticated session and record-ownership check protect this data.

Risk if the boundary is missing: an improperly authorized request could expose one candidate's application details to another user. This is a risk scenario, not a demonstrated issue.

Recommendation: require an authenticated principal for every candidate read and write; derive the permitted candidate/application scope from server-side identity and verify record ownership on every request. Treat URL identifiers as lookup keys only, never as bearer credentials. Return only fields needed for the screen, avoid logging full profile payloads, and apply private/no-store caching to personalized responses.

Low · Confirm

Page identifier and displayed reference code differ

Category: data integrity / supportability. Confidence: high for the visible discrepancy; its cause and impact are unknown.

Evidence: the candidate identifier in the page URL and the “Reference Code” shown in the page are not the same value. The values are intentionally not repeated here.

Risk: candidates or support staff may associate an action with the wrong tracking identifier; developers may also have difficulty correlating a page view with the correct application record.

Recommendation: define distinct, explicitly named fields for the internal application key and the candidate-facing reference code. Load both from the same authorized application record and test that the displayed code is stable and maps back to that record. Add a request/trace ID for diagnostics rather than exposing database keys in logs or UI.

Not assessed · Hardening

Submission validation and error handling need server-side guarantees

Category: input validation / reliability. The visible form labels show required and optional fields and a five-link maximum, but no input was submitted; server behavior is unknown.

Recommendation: enforce the link count, field lengths, URL parsing, and allowed schemes on the server. Reject malformed input with a clear 4xx response that does not reveal stack traces or internal details. If the application ever fetches a submitted URL, use a separately reviewed outbound-fetch design with strict destination controls; the simplest and safest option is not to fetch candidate-provided links on submission.

Not measured · Performance

Protect personalized responses and measure the critical path

No response timings, payload sizes, or cache headers were measured. For a dashboard of this shape, keep static assets cacheable and versioned, but make candidate-specific responses private and non-shareable. Measure page-data query latency and payload size with representative authorized test data before optimizing; avoid speculative caching of personal records.

06 / Action plan

Recommended improvements

Enforce ownership

Centralize authentication and application-ownership checks for every read and write. Deny by default and test cross-candidate isolation in a controlled environment.

Validate at the boundary

Use a typed request schema, server-side length/count limits, URL parsing, and consistent 4xx errors. Treat browser validation as usability only.

Improve observability

Correlate requests with a trace ID; log outcome, latency, and record key in a privacy-conscious form. Never log credentials or unnecessary profile details.

07 / Illustrative implementation

Example: authorize first, then validate

Illustrative TypeScript/Express-style pseudocode only; it is not based on a claim that Cynbit uses this framework. In production, use the application's existing authentication, schema-validation, and error-handling conventions.

const httpUrlSchema = z.string().url().max(2048).refine((value) => {
  try {
    const protocol = new URL(value).protocol;
    return protocol === "https:" || protocol === "http:";
  } catch {
    return false;
  }
});

const submissionSchema = z.object({
            primaryUrl: httpUrlSchema,
            additionalUrls: z.array(httpUrlSchema).max(4).default([]),
  notes: z.string().max(4000).optional()
}).strict();

app.post("/applications/:applicationId/deliverables", requireUser, async (req, res) => {
  const application = await applications.findById(req.params.applicationId);
  if (!application || application.candidateId !== req.user.id) {
    return res.sendStatus(404);
  }

            const input = submissionSchema.safeParse(req.body);
            if (!input.success) {
              return res.status(400).json({ error: "Invalid submission" });
            }

  const saved = await deliverables.save({
    applicationId: application.id,
    ...input.data
  });

  return res.status(201).json({ id: saved.id, status: "received" });
});
Important: adapt the schema to approved URL schemes and product requirements. The ownership check must use trusted server-side identity, and production code should handle persistence errors, concurrency, audit events, and idempotency using established project patterns.

08 / Follow-up

Authorized verification checklist

  1. In a staging environment with test accounts, confirm that one candidate cannot read or modify another candidate's application by changing identifiers.
  2. Check that missing/expired authentication and unauthorized ownership produce safe, consistent responses without leaking record existence or personal data.
  3. Submit boundary cases through the normal UI/API contract: zero and five total links, too many links, malformed URL, unsupported scheme, oversized notes, and duplicate submission.
  4. Verify the page reference code is derived from the same application record as the URL target, and that support tooling can correlate the event without exposing sensitive data.
  5. Measure representative dashboard latency and response size; review cache policy to ensure personalized responses are not stored in shared caches.

Conclusion: the visible experience gives candidates a clear staged workflow. Backend confidence depends on confirming ownership enforcement, input validation, and identifier consistency where the service can be tested safely and with authorization.
